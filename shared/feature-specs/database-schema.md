## 1. Overview

### What This Feature Does

This feature defines all SQLAlchemy async ORM models for the Ember database, generates the initial Alembic migration, and creates the complete relational schema in PostgreSQL. It produces seven tables: `profiles`, `characters`, `conversations`, `messages`, `user_activity`, `partners`, and `body_measurements`. It also creates all critical indexes required for cursor-based pagination and sorting.

### Why It Exists

Every API endpoint in Ember (auth, characters, messages, memory display, partners, body tracking) reads from or writes to these tables. Without the schema, no business logic can be implemented. This is the data foundation for all Phase 1 and beyond.

### Dependencies

- **Requires**: P01-01 (project-setup) -- provides `Base`, `TimestampMixin`, `AsyncEngine`, `AsyncSessionLocal`, Alembic env.py, and the complete directory structure.
- **Blocks**: P01-03 (user-auth), P01-04 (character CRUD), P01-05 (basic messaging), and all subsequent backend features that touch the database.

### What This Feature Does NOT Do

- It does not implement any API endpoints, route handlers, or service methods. Those are separate features.
- It does not implement Pydantic request/response schemas. Those are created alongside their respective route features.
- It does not seed any data. Seeding (e.g., default character templates) will be handled by later features.
- It does not add pgvector extension or vector columns. Vector search is handled by Mem0 cloud.

## 2. DB Changes

### Authoritative Source

The table definitions below are derived from `docs/04-veri-api.md`. Column names, types, and constraints follow that document exactly. Where the doc uses shorthand (e.g., "TEXT / NULL"), this spec translates to explicit SQLAlchemy column definitions.

### TimestampMixin Behavior (from P01-01)

The `TimestampMixin` from `backend/app/models/base.py` provides two columns:

- `created_at`: `TIMESTAMPTZ NOT NULL DEFAULT NOW()`
- `updated_at`: `TIMESTAMPTZ NOT NULL DEFAULT NOW()`, auto-updated on row change

Tables that inherit `TimestampMixin` get both columns. Some tables in the schema only need `created_at` (e.g., `messages`). The spec notes which tables use the mixin and which define `created_at` manually.

**File**: `backend/app/models/conversation.py`

- `user`: many-to-one relationship to `Profile`

### Table: `messages`

The highest-traffic table. Stores every message in every conversation.

| Column | SQLAlchemy Type | PostgreSQL Type | Nullable | Default | Constraints |
|--------|----------------|-----------------|----------|---------|-------------|
| `id` | `Mapped[uuid.UUID]` mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4) | `UUID PRIMARY KEY` | No | `uuid4()` | PK |
| `conversation_id` | `Mapped[uuid.UUID]` mapped_column(UUID(as_uuid=True), ForeignKey("conversations.id", ondelete="CASCADE")) | `UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE` | No | -- | FK |
| `user_id` | `Mapped[uuid.UUID]` mapped_column(UUID(as_uuid=True), ForeignKey("profiles.id", ondelete="CASCADE")) | `UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE` | No | -- | FK |
| `role` | `Mapped[str]` mapped_column(Text) | `TEXT NOT NULL` | No | -- | CHECK: `user` or `assistant` |
| `content` | `Mapped[str]` mapped_column(Text) | `TEXT NOT NULL` | No | -- | -- |
| `media_url` | `Mapped[str \| None]` mapped_column(Text, nullable=True) | `TEXT` | Yes | `None` | -- |
| `tts_url` | `Mapped[str \| None]` mapped_column(Text, nullable=True) | `TEXT` | Yes | `None` | -- |
| `metadata` | `Mapped[dict \| None]` mapped_column(JSONB, nullable=True) | `JSONB` | Yes | `None` | -- |
| `created_at` | `Mapped[datetime]` mapped_column(DateTime(timezone=True), server_default=func.now()) | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | No | `NOW()` | -- |

**Inheritance**: `Base` (does NOT use `TimestampMixin`)
**Table name**: `messages`
**Model class name**: `Message`
**File**: `backend/app/models/message.py`

**Relationships**:
- `conversation`: many-to-one relationship to `Conversation`
- `user`: many-to-one relationship to `Profile`

**Indexes**:
- PK index on `id` (automatic)
- **Critical composite index**: `idx_messages_conv_time` on `(conversation_id, created_at DESC)` -- the primary index for cursor-based message pagination. This is the most performance-critical index in the entire system.
- Index: `idx_messages_user_id` on `(user_id)` -- for user data deletion (GDPR) and activity queries

**Why no TimestampMixin**: The `messages` table does not need an `updated_at` column. Messages are immutable once written (append-only). Adding `updated_at` would waste 8 bytes per row on the hottest table and the `onupdate` trigger would fire on every row update, which never happens. The `created_at` column is defined directly on the model.

**Notes**:
- `role` is constrained to `'user'` or `'assistant'` via a CHECK constraint. This prevents invalid data at the DB level.
- `metadata` stores structured data like calorie estimates, intent actions, etc. It is JSONB (not JSON) for index-friendly querying if needed in the future.
- `content` has no DB-level max length. The 4000-character limit is enforced at the application layer (Pydantic validator) per `docs/standards/common.md` Section 8.
- `ON DELETE CASCADE` on `conversation_id` and `user_id`: deleting a conversation or profile removes all messages.

| `notifications_sent_today` | `Mapped[dict]` mapped_column(JSONB) | `JSONB NOT NULL` | No | `'[]'::jsonb` | -- |
| `updated_at` | `Mapped[datetime]` mapped_column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now()) | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | No | `NOW()` | -- |

**Inheritance**: `Base` (does NOT use `TimestampMixin`)
**Table name**: `user_activity`
**Model class name**: `UserActivity`
**File**: `backend/app/models/user_activity.py`

**Relationships**:
- `user`: one-to-one relationship to `Profile`

**Indexes**:
- PK index on `user_id` (automatic)

**Why no TimestampMixin**: This table has `updated_at` but no `created_at` (per `docs/04-veri-api.md`). The row is created when the user first becomes active and only `updated_at` matters thereafter. Adding `created_at` would be semantically misleading for an activity tracking table.

**Notes**:
- `user_id` is both the primary key and a foreign key to `profiles.id`. This ensures exactly one activity row per user.
- `notifications_sent_today` stores a JSON array of notification type strings sent today (e.g., `["morning_checkin", "evening_reflection"]`). Reset daily by a scheduled task.
- The server default for `notifications_sent_today` is an empty JSON array `'[]'::jsonb`.

- `status` is constrained to `'pending'`, `'active'`, or `'disconnected'` via a CHECK constraint.

## 4. Backend Logic

### Model Registration in `__init__.py`

The `backend/app/models/__init__.py` file must import all model classes so that Alembic's `autogenerate` can detect them. This is the canonical import point.

```
from app.models.base import Base, TimestampMixin
from app.models.profile import Profile
from app.models.character import Character
from app.models.conversation import Conversation
from app.models.message import Message
from app.models.user_activity import UserActivity
from app.models.partner import Partner
from app.models.body_measurement import BodyMeasurement
```

### Alembic env.py Update

The existing `backend/app/db/migrations/env.py` already imports `from app.models.base import Base` and sets `target_metadata = Base.metadata`. However, it does not import the model modules. The env.py must be updated to include:

```
from app.models import *  # noqa: F403 — ensures all models are registered with Base.metadata
```

This wildcard import (with the noqa comment to suppress the ruff warning) is the standard Alembic pattern documented in `docs/standards/backend.md` Section 14.

### Migration Generation

After all model files are created, the developer runs:

```bash
cd backend
alembic revision --autogenerate -m "create_initial_tables"
```

This produces a single migration file in `backend/app/db/migrations/versions/` that:
1. Creates all seven tables with their columns, types, and constraints
2. Creates all foreign keys
3. Creates all explicit indexes listed in the index summary above
4. Creates all CHECK constraints

The migration must be tested with both `upgrade` and `downgrade`:

```bash
alembic upgrade head     # apply migration
alembic downgrade -1     # revert migration
alembic upgrade head     # re-apply to confirm idempotency
```

### CHECK Constraints

Three tables use CHECK constraints to enforce enum-like values at the DB level:

1. `profiles.subscription_tier`: `CHECK (subscription_tier IN ('free', 'premium'))`
2. `messages.role`: `CHECK (role IN ('user', 'assistant'))`
3. `partners.status`: `CHECK (status IN ('pending', 'active', 'disconnected'))`

These are defined using `CheckConstraint` in the `__table_args__` of each model class.

## 8. Design Decisions and Rationale

### Why `messages` does not use `TimestampMixin`

Messages are append-only. They are never updated after creation. Adding an `updated_at` column with an `onupdate` trigger would waste 8 bytes per row on the highest-volume table and create a misleading schema that suggests messages can be edited. The `created_at` column is defined directly on the `Message` model.

### Why `user_activity` does not use `TimestampMixin`

The `user_activity` table as defined in `docs/04-veri-api.md` has `updated_at` but no `created_at`. Using `TimestampMixin` would add `created_at`, which is not part of the spec and is semantically unclear for an activity tracking table. The `updated_at` column is defined directly on the model.

### Why CHECK constraints instead of PostgreSQL ENUM types

PostgreSQL ENUMs require `ALTER TYPE` to add new values, which is cumbersome and requires migrations. CHECK constraints are easier to modify (drop old, add new) and work identically for validation. The `template` column on `characters` intentionally has no CHECK constraint because new templates are expected to be added dynamically.

### Why UUID primary keys on all tables

UUIDs prevent ID enumeration attacks, support distributed ID generation (no sequence contention), and match the Cognito `sub` format used for `profiles.id`. The trade-off is slightly larger indexes, which is acceptable for Ember's scale.

### Why `NUMERIC` instead of `FLOAT` for body measurements

Floating-point types (`FLOAT`, `REAL`, `DOUBLE PRECISION`) cause rounding errors with decimal values (e.g., 75.5 kg might be stored as 75.4999...). `NUMERIC(5,2)` and `NUMERIC(4,1)` store exact decimal values, which is important for health data that users expect to see displayed exactly as entered.

### Why one migration file for all tables

All seven tables are created in a single initial migration because they are all new and have no pre-existing data. Splitting into seven migrations would add complexity without benefit. Future schema changes (ALTER TABLE) will each get their own migration.

### Why ON DELETE SET NULL for `partners.user_id_2`

When an invitee deletes their account, the partnership record should be preserved (with `user_id_2 = NULL`) so the inviter can see that the partnership was disconnected. If we used CASCADE, the partnership record would vanish without explanation. The application layer handles updating `status` to `'disconnected'`.

## 9. Notes for Developers

### For backend-dev

- Start by creating all seven model files, then update `models/__init__.py`, then update `env.py`, then generate the migration.
- Use `uuid.uuid4` as the `default` on all UUID primary keys except `profiles.id` (which is set by the application from the Cognito sub).
- The `Mapped` type annotation style with `mapped_column()` is mandatory per SQLAlchemy 2.0. Do not use the old `Column()` style.
- For CHECK constraints, use `__table_args__` with `CheckConstraint`:
  ```python
  __table_args__ = (
      CheckConstraint("role IN ('user', 'assistant')", name="ck_messages_role"),
  )
  ```
- For composite indexes, use `Index` in `__table_args__`:
  ```python
  from sqlalchemy import Index
  __table_args__ = (
      Index("idx_messages_conv_time", "conversation_id", created_at.desc()),
  )
  ```
- The JSONB column for `metadata` and `notifications_sent_today` requires importing `from sqlalchemy.dialects.postgresql import JSONB`.
- The UUID type requires importing `from sqlalchemy.dialects.postgresql import UUID`.
- For `Numeric` columns, import `from sqlalchemy import Numeric` and for `Date`, import `from sqlalchemy import Date`.
- After generating the migration with `--autogenerate`, review the generated file carefully. Verify it includes all CHECK constraints and indexes -- Alembic sometimes misses named constraints on autogenerate.
- Test the migration against a real PostgreSQL instance (the Docker Compose DB from P01-01).

### For backend-tester

- Model definition tests (test_models.py) do not require a database connection. They inspect SQLAlchemy metadata objects in memory.
- Migration and constraint tests (test_migration.py) require a running PostgreSQL test database. Use the `conftest.py` fixtures from P01-01.
- When testing CHECK constraint violations, catch `sqlalchemy.exc.IntegrityError` and verify the error message contains the constraint name.
- When testing index existence, use `sqlalchemy.inspect(engine)` to get the index list for each table.
